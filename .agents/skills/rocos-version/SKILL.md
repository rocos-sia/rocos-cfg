# ROCOS Configurator 版本维护

## 必须遵守的项目约定

- 每次新建本仓库 Git 提交，都将应用版本更新纳入同一次提交，包括文档、设计、测试、构建和技能修改；不能先提交业务改动，再另建一个补版本提交。
- 软件当前处于测试阶段。发布渠道必须来自本次指令或会话中仍适用的明确约定，不能因为正在测试、当前版本带 rc，或上次选择了内部更新，就自动延用渠道。
- 用户只说“提交”“更新版本”而没有适用渠道指令时，先完成兼容性分析与其他检查，再询问内部测试更新还是正式发布。常规修正给出内部测试/patch 两个具体候选；新增功能或破坏性改动则给出相应 minor/major 候选与原因。
- 用户已经明确“内部测试”“rc 更新”“patch/minor/major 发布”或具体版本且无矛盾时，直接执行该选择，不重复确认。只说“正式发布”且所需级别可以根据改动明确判定时，说明判定后采用相应级别。
- 内部版本采用 `X.Y.Z-rc.N`，N 从 1 开始；正式版本采用 `X.Y.Z`。数字不带前导零，版本文件不带 `v`。
- 每次 patch、minor、major 正式版本提交成功后，必须在该提交上创建 `vX.Y.Z` 本地 Git tag。内部 rc 提交不自动打 tag。
- 本技能不单独授权 Git 提交、推送或远端发布。只编辑、评审或创建技能时不升版、不提交、不打 tag；用户要求本地正式发布提交时，所需本地 tag 属于该流程。

## 版本来源与同步

以仓库根目录 `VERSION` 为应用版本的唯一来源，内容为单行完整版本和结尾换行。

1. 读取工作区、索引和 HEAD 中的 `VERSION`，检查 `git status`、待提交 diff、当前分支历史及正式 tag。区分本次已准备的版本修改与已提交版本，不按字符串顺序比较版本。
2. 如果还没有 `VERSION`，查找现有应用清单和已发布 tag，说明可用基线。若均不存在，首次升版时提出初始版本建议（例如内部 `0.1.0-rc.1`）并确认；不要把文档里的 V1.2、归档 formatVersion 或其他仓库版本当成应用版本。
   当前桌面清单中的 `0.0.0` 是开发占位值；缺少 VERSION 和发布历史时，它不代表已经发布过 `0.0.0`。首次版本按用户确认的起始值建立。用户已经明确指定有效起始版本时，无需再次确认。
3. 检查已有 `package.json`、其锁文件中的根包版本、`src-tauri/Cargo.toml`、Cargo.lock 自身包版本、Tauri 配置和界面版本标识，按实际存在的文件同步应用版本字段或从 VERSION 生成。当前 Vite 构建从 VERSION 注入 `__APP_VERSION__`；未初始化时的 `development` 只是开发显示值，不能作为发布版本。不要为版本维护创建无实际用途的应用清单，也不要批量替换依赖版本或 workspace 成员版本。
4. 文档修订号、IgH `version: 1`、`.rcproj` 的 formatVersion/projectSchemaVersion 和模块格式版本独立维护。仅对应契约变化时更新，不与应用版本机械联动。

已有版本与 tag/清单矛盾、处于不明确的分支版本线，或首次版本来源有多种解释时，列出具体冲突与候选，再确定本次目标；不得凭空补造历史版本。

## 兼容性判定

参考 [SemVer 2.0.0](https://semver.org/lang/zh-CN/) 的主、次、修订三级语义。结合本项目，把以下内容视为需评估的公共契约：

- `.rcproj` 容器、manifest、模块契约，以及已保存工程能否无损重新打开。
- IgH/ECM/APP 配置导入导出格式、路径与文件保真行为、ENI 只读保证。
- 已公开的扩展接口、命令行、自动化入口和用户依赖的配置行为。
- 已承诺支持的平台或部署方式；撤销支持可能造成兼容性变化。

| 级别 | 判定 |
| --- | --- |
| patch | 向后兼容的问题修复、无契约变化的重构、文档/测试/构建/技能维护 |
| minor | 向后兼容的新功能、新可选字段/模块或公开接口弃用 |
| major | 破坏既有契约，旧工程/调用方式无法按承诺继续使用，或删除已有能力 |

判断是否破坏兼容性要考虑迁移能力和保真结果；能够无损自动迁移的格式升级不必仅因格式数字改变就判为 major。不要只根据改动行数、文件类型或提交前缀判断。

对 `0.x` 阶段也明确报告兼容性，不以“仍在测试”为理由把破坏性改动伪装为 patch。拟将破坏性更新从 `0.x` 推进到 `1.0.0` 时需说明其含义；若用户希望继续 `0.x`，先确认具体版本策略，不能自行改写规则。

正式发布评估的是当前发布线上相对最近已发布基线的累计变更，包含之前 rc 提交；不能只看最后一次小修正就把已积累的新功能标为 patch。对基线之后多类改动采用最高所需级别。用户指定 patch 但累计改动需要 minor/major 时，说明冲突并确认更合适的发布目标，不擅自发布错误级别。

评估对象是将要提交的完整快照：已提交的累计改动加上本次选定的改动。检查未跟踪文件是否属于本次提交范围，但不要把仍留在工作区、未纳入本次提交的功能算作本次发布内容；也不要遗漏已经暂存的变更。存在多条发布分支时，使用当前发布线的基线，不直接取仓库中数字最大的 tag。

## 确定版本号

先确定发布基线和目标数字核心 `T = X.Y.Z`，再决定是否添加 rc 后缀。除已验证的重试外，新版本必须高于对应提交基线且不复用已发布版本。

从正式基线 `X.Y.Z` 计算目标时：patch 为 `X.Y.(Z+1)`，minor 为 `X.(Y+1).0`，major 为 `(X+1).0.0`；minor 和 major 必须将低位归零。rc 晋升正式版则按下述候选目标规则处理，不再次增加数字核心。

- 从正式版本开始：按已确认的 patch/minor/major 计算下一个核心，内部更新为 `T-rc.1`，正式发布为 `T`。已经发布 `1.2.3` 后不能再生成更低的 `1.2.3-rc.1`。
- 当前为 `T-rc.N`，本次内部更新仍属于同一发布目标：使用 `T-rc.(N+1)`，不每次额外增加 patch。
- rc 周期中累计改动需要更高核心：先说明目标变化，按确认后的新核心从 `rc.1` 开始；后续小修正不降低已选择的发布目标。
- 当前为 `T-rc.N`，发布的是该候选版本对应的正式目标：去掉后缀得到 `T`。例如基线 `1.2.3`、当前 `1.2.4-rc.3`，确认 patch 发布后得到 `1.2.4`，而不是 `1.2.5`。
- 若候选版本核心已是 minor/major 目标而用户要求 patch，按累计兼容性与目标冲突处理，不能仅删除后缀并把它称为 patch。
- 用户指定完整版本时，检查格式、单调性、兼容性和 tag 冲突；不悄悄更换用户要求的版本。仅给具体 rc 核心但未给 N 时按已知序列选择下一个 N。

按数值比较各版本段及 rc 序号，例如 `1.2.4-rc.10` 高于 `1.2.4-rc.9`，且都低于 `1.2.4`。本项目不使用其他预发布后缀或构建元数据代替 `-rc.N`。

| 基线与当前状态 | 已确认操作 | 结果 |
| --- | --- | --- |
| 当前正式 `1.2.3`，兼容修正 | 内部更新 | `1.2.4-rc.1` |
| 当前 `1.2.4-rc.2`，目标不变 | 内部更新 | `1.2.4-rc.3` |
| 正式基线 `1.2.3`，当前 `1.2.4-rc.3` | patch 发布 | `1.2.4` + `v1.2.4` |
| 当前正式 `1.2.3`，兼容新功能 | minor 发布 | `1.3.0` + `v1.3.0` |
| 正式基线 `1.2.3`，当前 `1.2.4-rc.3`，新增功能 | 内部更新，确认新目标 | `1.3.0-rc.1` |
| 当前正式 `1.2.3`，破坏公开契约 | major 发布 | `2.0.0` + `v2.0.0` |

首次初始化没有可计算的发布基线，采用已经确认的起始版本，不假装它是从某个未发布版本推导出的 patch。

## 提交与 tag 流程

1. 检查本次提交范围、历史版本和 tag，完成改动对应检查；先给出兼容性结论和候选版本，再处理缺少的渠道信息。
2. 确认渠道/目标后更新 VERSION 及实际存在的消费字段。若本次变更已经准备了符合决定的版本修改，直接复用；提交失败后重试不能再递增一次。
3. 仅暂存本次提交范围内的改动和对应版本文件，保留无关工作区改动；不要为了升版把其他未提交工作一并纳入。提交前检查暂存内容和 `git diff --cached --check`，确认版本与业务改动在同一提交中、正式 tag 名未占用。核对暂存快照中的 VERSION、应用清单和锁文件自身包版本一致；采用构建时读取 VERSION 的字段不必重复写入。只有版本修改请求而没有提交授权时，留在工作区并报告，不擅自提交。
4. 用户授权提交后创建提交，记录 commit SHA。正式发布随后用已验证的精确版本创建附注 tag，例如 `git tag -a v1.2.4 <commit-sha> -m 'Release v1.2.4'`；tag 必须指向包含同版本 VERSION 的提交。
5. 验证提交内 VERSION、tag 指向和工作区状态。报告旧版本 → 新版本、发布渠道、commit SHA 和 tag；未提交时只报告文件变更。

不得强制覆盖、删除或移动已有正式 tag。正常新发布遇到同名 tag，先检查冲突，不能把改名 tag 当作解决办法。若是恢复本次已成功提交的发布操作，且 tag 已指向同一提交并且版本一致，可认定该步骤完成；指向不同提交则停止发布并报告。

如果提交成功而 tag 创建失败，明确报告这两个不同结果；修复后只补建该提交的 tag，不重做提交或再次升版。未经用户明确要求不推送 commit/tag，不创建 GitHub Release。远端状态未经检查时不宣称 tag 在远端也可用。

不为套用新规则重写已有历史提交。用户要求 amend 时，检查被替换提交的版本准备情况，避免对同一次失败/修正重复升版；已正式打 tag 的发布提交不得被静默改写。

## 调用示例

- “创建 Git 提交”：完成检查后，给出具体内部版本与正式版本候选，等待用户选择渠道再更新版本并提交。
- “创建 Git 提交，内部测试更新”：按兼容性确定目标核心，递增或开始 `rc.N`，将版本与改动一同提交。
- “创建 Git 提交，发布 patch 版本”：检查相对最近正式版本的累计改动；兼容级别符合时提交正式版本并创建 `vX.Y.Z` tag。
- “本次作为 minor / major 发布并提交”：按对应级别确定正式版本，提交后创建相应 tag。
- “只修改功能，暂不提交”：完成改动，保留现有版本，等实际准备提交时再执行本技能。
