# 工程模型迁移

当前已实现并提交的容器及工程模型均为 v1，没有更早的正式格式。应用 `VERSION`、容器 `formatVersion`、工程 `projectSchemaVersion`、模块版本和目标主站/APP 版本彼此独立；添加迁移基础设施不人为增加这些格式版本。当前 v1 工程按原流程打开，不复制全部资源来运行空迁移；未知版本继续只读预览和逐字节原包复制。

`src/core/project/migrations.ts` 提供编译期 `MigrationRegistry`。归档只能携带声明式数据，不能登记或执行迁移代码。每个步骤具有稳定 ID、说明和相邻版本 `N → N+1`，源版本和目标版本都必须有完整校验器。缺少中间步骤、未知版本、降级、重复 ID 或试图改变容器契约都会拒绝执行。

迁移在 Worker 的暂存副本上进行：先校验源数据，再逐步转换并校验每一步输出，最终交给当前归档解码器。输入、输出、校验器和转换函数不共享调用方可变数据；中途失败不会返回部分工程，也不会替换当前工作区或改写原包。迁移函数必须是确定性的纯数据转换，不使用时间、随机数、网络、文件系统或设备访问。文件清单、路径、大小、SHA-256 和总量限额必须在对应 Schema 校验器中检查。

工程模型升级仅处理工程元数据和编辑状态，不升级主站/APP 配置契约。已有配置、ENI、模型、资源和附件按稳定文件 ID 保留原始字节及元数据；允许改变包内路径，但不能顺带修改内容或角色。已有非编辑状态模块的声明也必须保留，包括未知可选模块的私有字段。模块格式升级或原生配置转换需要各自的显式方案，不能借工程模型迁移静默执行。

成功准备后返回版本链、每步说明、manifest 是否变化和变化的文件路径。界面先显示迁移预览，可取消或复制原始工程包；只有确认后才切换工作区。已有工作区还会单独提示替换。迁移后的工程处于未保存状态，桌面通过现有 `ProjectSession` 的受保护来源机制保留原文件授权：首次保存选择新路径，后续另存及副本导出也不能覆盖本会话的原包。浏览器端生成下载文件，不直接写入原文件路径。原路径授权不写入工程归档。

后续引入真实 v2 模型时，需要同时完成：

1. 保留 `ManifestV1` 和 `validateManifestV1` 的历史契约，实现独立 v2 校验器，并调整当前模型的保存/解码入口。
2. 在 `archive.ts` 的 `projectMigrations` 中登记真实 `1 → 2` 转换和两个版本的校验器；转换负责更新 manifest 版本、编辑状态索引和实际改变文件的哈希。
3. 加入真实旧版 `.rcproj` 契约样例，验证旧版打开、迁移报告、原包复制、首次另存、新版重新打开、失败回滚以及未知可选模块/草稿/资源保真。不能用当前版本样例改个版本数字代替历史样例。
4. 在网页离线包和桌面实际文件对话框上完成同一条真实迁移链的验收，再声明支持该旧版本。

现有测试覆盖迁移算法的两步测试链、失败回滚、校验顺序、非法链、ENI/资源/模块保真、编辑状态变更报告，以及真实 v1 的无迁移打开和未来版本只读处理。浏览器测试在真实归档解码后注入**测试报告**，覆盖预览、取消、原包复制、确认切换和下载；它不证明存在真实旧版格式迁移。受保护保存路径沿用文件会话测试和桌面恢复流程已验证的机制，真实版本迁移的桌面验收仍随首个格式升级补充。

```sh
npm test -- tests/migrations.test.ts tests/archive.test.ts tests/file-access.test.ts
npm run test:ui -- tests/browser/migration.spec.ts
```
